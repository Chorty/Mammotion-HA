# 🔑 Arcs work, and `toward` tracks them — the night route is open

**2026-08-12, two armed daylight pulses on `0.6.4-beta45`.** Both authorized,
gate armed for each and disarmed with the state verified. Blades off. Evidence:
`docs/evidence-arc-probe-20260812.json` and
`docs/evidence-linear-control-20260812.json`, plus the settled positions
recovered by polling afterwards (see §4 — the probe could not see its own
motion).

## 1. The result

Back to back, same speed, same 2000 ms window, same 200 ms cadence, one variable
apart:

| | command | displacement | course change |
| --- | --- | --- | --- |
| **arc** | `linear 400, angular 180` | **0.5823 m** | **+22.20°** |
| **linear** | `linear 400, angular 0` | 0.5840 m | +0.00° |

**The distances differ by 1.8 mm and the courses differ by 22.20°.** The angular
axis added rotation without changing how far the mower travelled. That is about
as clean a controlled pair as this project has produced, and it was accidental —
the linear pulse was run as a diagnostic to test whether the mower was moving at
all, not designed as a control.

Arc geometry, from the chord and the turn:

```
chord            0.5823 m
course change   22.20 deg
implied radius   1.512 m          arc length 0.5859 m  (consistent with the chord)
turn rate       11.10 deg/s over the window
```

The arc length agreeing with the chord to 3.6 mm says this really is a circular
arc rather than a skid.

## 2. 🔑 Why it matters: `toward` tracked the rotation exactly

**This was the whole question.** `docs/night-motion-options-20260811.md` argued
that an arc is the only route to night capability, because translation keeps
`toward` (course-over-ground) live, and a live `toward` closes a heading loop
with **no VIO at all**. The open risk was whether course-over-ground actually
follows an arc closely enough to steer on.

It moved **22.20°** while the mower turned **22.20°**. The linear control moved
**0.00°**. The mechanism a night controller needs is confirmed on hardware.

## 3. 🔑 "Angular needs 500" is a STATIONARY-only finding

The 2026-07-25 A/B established that motion refresh is speed-gated: it unlocked
linear at 400 but *"did NOTHING for the turn at angular 180 (~3° total)"*, which
is why every VIO turn in this project uses `vio_angular_speed: 500`.

**Angular 180 actuated fine in an arc** — 22.2° in two seconds. The earlier
result stands for what it measured, a *pure in-place turn*, and does not
generalise: a stationary skid-steer has to break static friction on both tracks,
while a moving one only needs a differential between them. Do not carry "angular
must be 500" into arc work.

## 4. ⚠️ The probe was blind to its own motion, and nearly produced a false negative

The arc run reported **four bit-identical position samples** and an unchanged
`toward`. On that record the run reads as "no motion", and it was about to be
written up as *"the arc did not actuate"*. It was the operator saying the mower
had moved that stopped it.

The mower does not push position while stationary, so once a pulse ends nothing
updates the coordinator cache until something asks. The real executors all call
`_refresh_position_after_raw_motion` (`request_reports_count_5`) and then
`_settle_linear_position_feed`; `raw_pymammotion_motion_probe` was the one motion
path that did neither. The arc's true position appeared in the cache roughly
**five minutes** later, and the linear control's about **2.5 minutes** later.

Fixed in beta45: the probe now forces the refresh and waits for the settle, with
a test that asserts the source calls both.

**Method note worth keeping.** Bit-identical telemetry is evidence of a stale
feed, not a stationary mower — this project has written that rule down twice
before and it was still nearly missed here. The reasoning that failed was
"position updates ~1 Hz during motion, so an old frozen value means no motion";
it is only valid if something is actually driving the feed.

## 5. What is NOT established

- **One arc, one radius.** 1.512 m at `linear 400 / angular 180`. The
  radius-versus-angular relationship is unmeasured, and an `arc_to_point`
  controller needs it.
- **No closed loop was run.** This is an open-loop pulse. Whether a controller
  can *steer* on `toward` — as opposed to `toward` merely reporting correctly —
  is untested.
- **Nothing was tested at night.** Both pulses ran in daylight, deliberately, so
  VIO was available as independent ground truth. The night claim rests on the
  mechanism plus the vendor's own dock return, not on our own dark run.
- **`toward` latency during an arc is still unmeasured** at the pulse timescale;
  what §1 shows is the settled value after the pulse, not tracking during it.

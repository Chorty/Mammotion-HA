# Mammotion Android APK feature catalog: onboarding and connectivity

## Scope and coverage

This report catalogs device onboarding, binding, connectivity, and transport behavior substantiated in the decompiled Mammotion Android application under:

- `src/sources/com/agilexrobotics/bind/`
- `src/sources/com/agilexrobotics/espressif/`
- `src/sources/com/agilexrobotics/command/bleconnect/`
- `src/sources/com/agilexrobotics/iot_module/`
- `src/sources/com/agilexrobotics/maiot_module/`
- `src/sources/com/agilexrobotics/device/source/`
- `src/sources/com/agilexrobotics/signal/`
- `src/resources/AndroidManifest.xml` and relevant `src/resources/res/` entries

Paths below are relative to `/Users/mattjoslin/mammotion-apk-decompile/`. The source tree contains 451 files in the seven requested package roots (87 bind, 26 Espressif, 2 command/BLE-connect, 42 legacy IoT, 49 MA-IoT, 142 device-source, and 103 signal files). Generated `R`, data-binding, Hilt/Dagger, and `BuildConfig` files were inventoried but are not treated as behavioral evidence. Unrelated third-party implementation internals were excluded; references to Paho, Ali IoT, LitePal, or Android APIs are included only where primary Mammotion code uses them.

The strongest architectural conclusion is that the application has two runtime command paths:

1. **Local BLE:** binary/custom bytes are written through Espressif BLUFI/GATT.
2. **Remote IoT:** JSON/protobuf content is sent through a Mammotion cloud service-invocation API, with MQTT used primarily for asynchronous downlink/status/event delivery.

The link manager automatically moves between BLE and IoT based on BLE failures, Bluetooth state, network availability, and reported device cloud presence. “Wi-Fi” and “4G” are generally device uplinks feeding the same IoT/cloud path rather than independent app-to-device transports.

## Command and protocol details

### Espressif BLUFI over BLE

- GATT UUIDs are:
  - service `0000ffff-0000-1000-8000-00805f9b34fb`
  - write characteristic `0000ff01-0000-1000-8000-00805f9b34fb`
  - notification characteristic `0000ff02-0000-1000-8000-00805f9b34fb`
  - CCC descriptor `00002902-0000-1000-8000-00805f9b34fb`
  (`src/sources/com/agilexrobotics/espressif/params/BlufiParameter.java:18-21`).
- Control subtypes include security-mode setup (1), operation-mode setup (2), connect Wi-Fi (3), disconnect Wi-Fi (4), Wi-Fi status (5), deauthenticate (6), version (7), close (8), and Wi-Fi list (9). Data subtypes include negotiation (0), station SSID (2), station password (3), custom data (19), error (18), and certificate/key payloads (`BlufiParameter.java:26-49`).
- Frames carry type/subtype, sequence, payload length, and frame-control flags. The implementation supports encrypted, checksum, direction, acknowledgment, and fragmentation bits (`src/sources/com/agilexrobotics/espressif/FrameCtrlData.java:8-53`; `src/sources/com/agilexrobotics/espressif/BlufiClientImpl.java:746-845`).
- Security negotiation uses Diffie-Hellman/key exchange, MD5-derived material, AES encryption, and CRC checks. The implementation turns on encrypted/checksummed transport after negotiation (`src/sources/com/agilexrobotics/espressif/BlufiClientImpl.java:309-411`; `src/sources/com/agilexrobotics/espressif/security/BlufiDH.java:20-79`; `BlufiAES.java:19-97`; `BlufiCRC.java:8-17`).
- The app targets MTU 200 and enforces a package-length limit with fragmentation for larger custom payloads (`src/sources/com/agilexrobotics/device/source/links/managers/EspBleManager.java:63`; `src/sources/com/agilexrobotics/espressif/BlufiClientImpl.java:849-951,1543-1548`).

### Cloud API and MQTT

- MA-IoT authentication discovers region, logs in with signed headers, refreshes account/MA tokens, and then requests an MQTT JWT. Relevant API paths are collected in `src/sources/com/agilexrobotics/maiot_module/utils/Constants.java:18-60`; signed header parameters are visible in `MaIoTApiService.java:66-94`.
- Commands are not shown as direct MQTT publishes in the scoped command path. They are HTTP service invocations to `/v1/mqtt/rpc/thing/service/invoke`, normally using identifier `device_protobuf_sync_service`; responses are fed to the same command callback layer (`MAIotManager.java:44,633-743`).
- MQTT handles asynchronous thing status, property reports, log progress, and protobuf events. `MQTTService` caches subscriptions and resubscribes after reconnect (`MQTTService.java:272-384`; `MQTTClient.java:283-402`).
- The cloud downlink model carries a topic-derived device name, method/identifier, JSON params, message ID/version, and time. The protobuf/event payload is subsequently handed to the device data receiver (`TopicProperty.java:15-91`; `TopicUtils.java:21-43`; `MAIotManager.java:333-359`).

### Transport routing semantics

```text
command producer
  ├─ selected link = BLUETOOTH → protobuf/raw bytes → BLUFI custom data → GATT
  └─ selected link = IOT       → JSON/service request → Mammotion RPC
                                           ↓
                         MQTT status/property/protobuf downlink

BLE failure/off/timeout + phone network + device online → IOT
Wi-Fi close / Bluetooth restored / explicit BLE probe   → BLE attempt
neither usable                                           → NONE/offline
```

The diagram describes code behavior, not a guarantee that every command is byte-for-byte identical across transports. The actual high-level protobuf command definitions lie mostly outside the requested package scope.

## Proxy-like or relay behavior

No general-purpose TCP/UDP proxy, port forwarder, HTTP proxy, SOCKS proxy, or local network bridge was substantiated in the scoped primary app code.

There **is protocol relay-like behavior** in the narrow sense that the app wraps device protobuf content in a cloud service invocation (`device_protobuf_sync_service`) and receives protobuf events through MQTT. This is an application-level command tunnel, not evidence of a generic proxy. `MALinkManager.postCustomeDateByte` sends only through BLE, while `postJsonString` sends only through the IoT manager (`MALinkManager.java:410-425`). A stray ZeroMQ import in `device/source/device/utils/StringUtils.java` is a constant/library artifact and does not establish proxy behavior.

## Hidden and diagnostic features

- **Auto-test transport override:** `setCurrentLinkTypeForAutoTest` can force the current link status, and extensive logs are tagged by BLE, pairing, and source (`MALinkManager.java:501-510`).
- **Background BLE probing while on IoT:** when IoT comes online and no usable link exists, the app selects IoT and can start BLE scan/connect with a short argument (`MALinkManager.java:284-303`).
- **Cloud stop-message recovery:** `requestIOTStopMessage` invokes a stop command with callback/error handling, implying a safety/recovery path over IoT (`MAIotManager.java:752-809`).
- **Separate “error” cloud presence query:** failures can trigger a less-throttled error status path instead of the normal five-minute status request (`MAIotManager.java:477-566`).
- **Factory LoRa reset and RTK relink:** strings and settings expose restoration of a factory LoRa number, RTK reference-station reset, reconnect, and mode switching (`strings.xml:478,557,735,751`; `RTKSettingActivity.java:3810-4280`).
- **Pool-robot encryption endpoint:** `/device-server/v2/pool-robot/encryption` returns encryption material for pool-device operations (`DeviceSourceApiService.java:25-27`; `EncryptionReq.java:10-61`; `EncryptionResp.java:10-72`).
- **Device-side Wi-Fi scan telemetry:** logs include every SSID/RSSI/security type. This is useful diagnostically but risks exposing nearby network names (`EspBleManager.java:173-186`).
- **Internal/forward-looking model labels:** KM01, HM433/HM610, MN100/MN101, SDPX, LUBA mini LiDAR/Vision, LUBA 3, and RTK NB appear in model tables even if availability may be server/resource gated (`SelectDeviceTypeViewModel.java:72-163,283-363`).

## Home Assistant implementation implications

1. Represent one physical device with a transport coordinator, not separate BLE and cloud entities.
2. Treat BLE custom-data and cloud service invocation as two envelopes around device command protobufs.
3. Prefer MQTT for push telemetry/presence, but obtain and refresh broker credentials through Mammotion’s authenticated HTTP flow.
4. Keep a compatibility seam for legacy Ali-IoT devices.
5. Persist product key, device name/serial, IoT ID, model/service item code, and BLE address separately.
6. Capability-gate Wi-Fi, 4G/SIM, RTK/iNavi, LoRa, VIO, and pool features by model plus observed properties; static model names alone are insufficient.
7. Redact Wi-Fi passwords, MQTT JWTs, access/refresh tokens, ICCIDs, nearby SSIDs, and device encryption material from diagnostics.
8. Expose transport, cloud presence, BLE status, Wi-Fi/4G signal, SIM state, RTK source/link/signal, and last error as diagnostics. Make binding, provisioning, SIM activation, RTK source changes, and LoRa resets explicit user actions.

## Uncertainties and decompiler caveats

- Decompiled Kotlin produces large metadata annotations, synthetic lambdas, renamed fields such as `f10834a`, and occasional failed control-flow reconstruction (`UnsupportedOperationException` stubs). Method names and constants are generally reliable; exact branch ordering in heavily reconstructed methods is less certain.
- Resource strings prove shipped user-facing capability text, not necessarily reachability for the current account, country, app build, or device. This report pairs strings with primary code where possible and labels resource-only diagnostics accordingly.
- Server-driven product lists, guide resources, account entitlements, region, firmware, and feature flags can hide or enable models/features at runtime.
- “Wi-Fi” and “4G” are reported as device network types, but scoped code does not expose separate app command sockets for them. Both appear to converge on IoT/cloud control.
- MQTT topic constants identify event suffixes/categories, but complete concrete topic strings are obtained or composed across runtime/backend code. Runtime capture is recommended before implementing subscriptions.
- The app contains both legacy Ali IoT and newer MA-IoT layers. Static analysis cannot prove which backend each production account/device currently receives.
- BLUFI security code is substantively present, but reproducing it requires packet-level interoperability testing; decompiled code should not be treated as a normative protocol specification.
- The complete mower command protobuf schema is largely in `com/agilexrobotics/command/` outside the specifically requested `command/bleconnect` scope. This report therefore documents transport envelopes and onboarding commands, not every mower operation.
